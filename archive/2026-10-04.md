## 1. 「手段を3つに絞れ」「自分で採点しろ」は効く? 60回比べたら、効果より採点の落とし穴が出た

kanta13jp1さんの記事。AIへの指示として紹介されがちな2つの手法、使ってよい手段を3つに限定することと、正しさの条件を自分で挙げて自己採点させることを、同じ課題・同じモデルで4条件×15回、計60回比べている。結果は、どの条件でも全問合格の回数やチェック合格率が近く、精度が上がるとは言えなかった。各条件15回では、この程度の差は偶然の範囲に収まるという。むしろ目立ったのは、採点のやり方そのものに落とし穴があったことだ。定番とされる手法を鵜呑みにせず、自分の課題で測り、サンプルが小さいことまで含めて結論を控えめに書く姿勢が参考になる。

出典: https://zenn.dev/kanta13jp1/articles/prompt-constraint-selfcheck-60-trials

## 2. Claude Code を毎時起動して、クオンツ研究を仮説から本番投入まで無人で回している仕組み

toshiponさんの記事。暗号資産の先物を少額で取引するクオンツ研究のリポジトリで、Claude Codeを1時間おきに起動し、次の一手を人間の承認なしで進めさせている。設計の要点は、判断をLLMに任せきりにしないことだ。起動するかどうかはシェルスクリプトが決め、理由がなければLLMは起動しない。次にやる行動もコードが10種類の中から1つ選び、Claude Codeはその1つだけを実行してPRを出す。自律的なエージェントを長期運用するときに、どこまでをコードで固定し、どこからをモデルに委ねるかの線の引き方を、具体例で見せてくれる。

出典: https://zenn.dev/toshipon/articles/autonomous-loop-decision-table

## 3. Claude Codeのcompactionをロスレスにしたら、52秒が0.26秒になった

yottayoshidaさんの記事。Claude Codeの組み込みcompactionは、会話をモデルに要約させる仕組みである。筆者の環境で約57万6千トークンの会話を処理すると約52秒かかり、しかも要約に入らなかった情報は次のコンテキストに残らない。この2点が不満で、モデルに要約を書かせず、会話を損なわずに圧縮するプラグインlossless-compactionを作ったという。同じ会話で0.26秒まで縮んだとのことだ。ただしこれは筆者の環境での計測であり、方式の違いによる得失は読んで確かめたい。長いセッションを日常的に回す人にとって、待ち時間と情報の欠落という、compactionの2つの痛みを同時に扱う試みである。

出典: https://zenn.dev/yottayoshida/articles/lossless-compaction-v070

## 4. AIに同じ操作をもう一度頼む前に。二重実行を防ぐリトライ設計

AI師範さんの記事。AIに外部操作を任せるとき、失敗そのものより厄介なのは「結果が分からない」状態だと整理している。たとえば記事の公開操作で、サイト側では公開が済んだのに、応答が返る前に接続が切れたとする。AIから見ると成功の表示はないので、同じ操作をやり直して二重投稿になる。「返事がない」ことは「実行されていない」ことではない、という区別が出発点だ。失敗と不明を別の状態として扱い、再試行の前に結果を確かめる設計が必要になる。分散システムでは古くからある話だが、エージェントに操作を委ねる場面で改めて問われる点である。

出典: https://zenn.dev/ai_shihan/articles/11f2aa9df789da

## 5. Claude Code の usage limit 自動継続を止めていたのは Remote Control だった

daydreamerさんの記事。usage limitのリセット後に作業を続ける自動継続は、既定で有効のはずだった。ところがRemote Controlのセッションでは自動では始まらず、画面にも何も出ない。筆者の履歴では、Remote Controlに接続した状態で上限に当たった10回は1回も始まらず、接続していなかった8回は8回とも始まったという。筆者が探した範囲では、この挙動が書かれているのはinteractive-modeのページだけだった。対策として、StopとStopFailureのhookを使い、リセットまで待って作業を再開させる方法を紹介している。無人で長時間回す使い方をしている人は、一度自分の環境を見直す価値がある。

出典: https://zenn.dev/daydreamer/articles/claude-code-usage-limit-auto-resume

## 6. 熟練者の手順はワークフローに、小さな「なぜ」はメモリに残す

kyrenzkさんの記事。エージェントはコードを書くのが速い反面、目的を飛ばしたり、先週却下した案を別のセッションでまた出してきたりもする。足りないのはモデルの賢さというより、着手前に踏む段取りと、ADRにするほどではない小さな判断の残り方だと筆者は見る。手順はチャットの中で溶け、小さな「なぜ」は会話が閉じると消える。そこで、熟練者の手順は再利用できるスキルとして、小さな判断はメモリとして、会話の外に残す。枠組みの着想はCursor上のプロセススキルから得ているが、記事はその使い方の紹介ではなく、考え方の整理に主眼を置いている。

出典: https://zenn.dev/kyrenzk/articles/workflow-and-engineering-memory

## 7. AuroraのI/O料金はオンプレのIOPSから換算できない

techdbblogの記事。オンプレのデータベースをAurora PostgreSQLへ移行するとき、インスタンス料金とストレージ料金はスペックから計算できる。残るのがAurora StandardのI/Oリクエスト料金で、既存環境のIOPS統計に係数を掛けて概算しようとすると、根拠が示せず見積もりが止まる。記事の結論は、IOPSからの換算は成り立たないので、検証環境で代表的なワークロードを流し、CloudWatchのVolumeReadIOPsとVolumeWriteIOPsを実測して月間値へスケールする、というものだ。移行前の見積もりで「もっともらしい係数」に頼りたくなる場面で、実測に倒す判断の根拠になる。

出典: https://zenn.dev/techdbblog/articles/techdb-aurora-io-cost-estimate
