## 1. Aurora MySQL の監査ログとgeneralログ両方出すのもったいなくない？

team_deltaさんの記事。Aurora MySQLで監査ログとgeneralログを両方CloudWatch Logsに出力している運用に対し、著者は中身がどこまで重複しているかを調べている。generalログはクライアントの接続・切断とSQL文の受信をそのまま記録するのに対し、監査ログは同じ情報に加えて失敗したクエリやメタデータも記録しており、実質的にgeneralログの内容を包含していることが分かった。ただし無効化前には、監査ログ機能が有効でクエリとコネクトの両方のイベントを記録する設定になっているか、ユーザー絞り込みのパラメータを使っていないか、generalログの保存自体が監査要件で義務付けられていないかを確認する必要があるとしている。CloudWatch Logsの課金はほとんどが取り込み量に比例するため、重複出力をやめるだけでクエリ量の多いクラスターほど大きな削減効果が見込めるという。一方で実行時間はどちらのログにも記録されないため、パフォーマンス分析にはスロークエリログが別途必要になる点は変わらないと注意を促している。

出典: https://zenn.dev/team_delta/articles/e8b234e90430ab

## 2. AWS Cost Explorerだけでは気づけない「隠れコスト」5選

cloudcutさんの記事。AWSのコスト削減というとSavings PlansやReserved Instancesが語られがちだが、著者はCost Explorerの月次サマリーだけでは気づきにくい「地味に効いている」コスト項目を5つ整理している。外部API呼び出しの多いマイクロサービスでは、NAT Gatewayの時間課金以上に通過データ量に応じた処理料金が効いてくるため、S3やDynamoDBはVPCエンドポイント経由に切り替えるといった設計変更が有効だという。同一リージョン内でもAZをまたぐ通信には転送料がかかり、マルチAZ構成では積み重なっていくため、使用タイプ別の内訳で存在を確認すべきとしている。ほかにも、ライフサイクルポリシーを設定していないEBSスナップショットがCI/CDでのAMI更新のたびに無限に蓄積していくケース、保持期間を設定していないCloudWatch Logsのロググループに開発環境のデバッグログが溜まり続けるケース、インスタンスからデタッチされたまま放置されたElastic IPアドレスに時間課金が発生し続けるケースを挙げ、それぞれ具体的な対策を示している。個々の金額は小さくても、複数アカウントやリージョンにまたがると合算で無視できない規模になりうると締めくくっている。

出典: https://zenn.dev/cloudcut/articles/aws-hidden-costs-5-checkpoints

## 3. AIのAPI化でクラウド費用が「見えなくなる」構造

cloudcutさんの記事。生成AIのコストというとトークン単価の議論に寄りがちだが、著者は実務で請求書を並べていて厄介なのは単価ではなく、誰にいくら払っているのか社内の誰も全体像を把握していない状態だと指摘する。企業がAIを座席課金のSaaSからAPI統合に移行すると、請求は座席課金のSaaS費用、APIのトークン代、ベクトルDBや推論サーバーなど周辺のクラウドインフラ費用、社内の開発・保守人件費という性質の異なる4枚に分かれてしまい、特に周辺インフラ費用は普通のクラウド請求に紛れ込んでAI関連費用として識別されなくなるという。この記事は「AIでクラウド費用が急増する」という主張ではなく、著者はむしろ自分から逆風データを並べる。国内のAI関連インフラ支出の年平均成長率は7.3%程度にとどまり、期待を大きく超える成果を実感している企業は1割に満たず、機能面の効果は出ていても経営指標への効果は不明確という企業が大多数だという。加えて使用量が変わらなくても円安の進行だけで支払額は数年で1割以上増加しており、この請求先が分散して総額が見えなくなるという構造は、AI投資の規模が伸びても縮んでも成立する、市場予測ではなく請求書の物理的な構造の問題だと結論づけている。

出典: https://zenn.dev/cloudcut/articles/ai-api-cloud-cost-invisible

## 4. 実装したAIにレビューさせない——Claude Codeの3パス独立レビューと機械判定

tukiyubiさんの記事。以前は実装させたAIにそのまま同じ会話でレビューを頼んでいたが、実装時の対話には設計理由や試行錯誤の経緯がすべて残っているため、そのAIにレビューさせると自分の実装を追認する方向に寄りやすいと著者は気づいた。そこで実装担当のAIとレビュー担当のAIの会話を分け、さらにレビューを3つのパスに分割する仕組みを実案件で数か月運用している。1回目と3回目のパスはあえて仕様を開示せず、それぞれコード単体の欠陥、変更していない既存コードへの影響を独立に探らせることで、仕様を知らないことを逆に武器にして設計上の思い込みを避けている。2回目のパスでは仕様を開示したうえで、承認済みの要件との整合性や範囲外の変更がないかを確認する。AIの判定を全面的には信用せず、レビュー結果はJSON形式に固定して内容を可視化し、変更ファイル一覧やテストの成否、前回指摘への対応状況はgitやシステムから直接検証したうえで、致命的な指摘が未解決のまま残っていればブロック判定にする仕組みも組み込んだ。初期は差分に関わらず毎回フルレビューしていたためトークン消費が急増した反省から、2回目以降は前回との差分だけをレビューし、大きな設計変更があったときだけフルレビューに戻すという運用に落ち着いたという。

出典: https://zenn.dev/tukiyubi/articles/289ddb13e112b9

## 5. 表に2行足したら、検査も2件増えた ── CLAUDE.md のドキュメントドリフトを exit code で検知する

aizuchi_worksさんの記事。CLAUDE.mdのようなエージェント向けの指示ファイルを育てていくと、「このパスを見ろ」という契約を示す正本パスの表ができあがるが、ディレクトリを1つリネームしただけでその契約は静かに嘘になってしまう。テストは散文までは検査しないため何も壊れず、次にその表を頼ったエージェントは存在しないパスから推測を始めることになる。著者はこの問題に対し、指定した見出し下の表を読み取り、2列目に書かれたバッククォート付きのパスが実際に存在するかを検査する自作ツールops-assertを作った。PowerShellだけで書かれた依存のない実装で、表に行を追加すれば検査項目も自動的に増える。導入直後は20件だった検査が、3日後に表へ2行追加しただけで22件に増えたことで、仕組みが狙いどおり機能していることを確認している。あわせて、誤検知が3回連続で出たアサーションは削除する、検査全体が30秒を超えたら縮小するといった撤退の基準もあらかじめ決めており、信用されない検査は無いよりも有害だという考えに基づいて運用している。

出典: https://zenn.dev/aizuchi_works/articles/402ac5f5118c64

## 6. AWS の外向き通信を制限したい。Network Firewall は月 $290 — どう代替し、何を諦めたか

yookさんの記事。前回の記事ではFly.io+NeonからAWSへ個人開発サービスを移行した際に、外向き通信をegress proxy一本に集約したことだけ触れていたが、今回はその構成に行き着くまでの設計の試行錯誤を記録している。実現したかったのはどのタスクがどの外部ホストに通信できるかを許可制で管理することだが、専用のマネージドサービスであるAWS Network Firewallは月額290ドルと個人開発には高額で、正面から使うのは見送った。代わりにOSSのSquidをECS Task上でフォワードプロキシとして常駐させ、そこから先だけNAT Gatewayを通す構成を採用し、月額はプロキシとNAT Gatewayを合わせて60ドル程度に抑えた。当初はプロキシにパブリックIPを持たせてNAT Gatewayのコストそのものを削るという案にも傾いたが、自前のコンポーネントはインターネットにアドレスを持たないという安全基準を優先し、NAT Gatewayのコストを受け入れる判断に転換している。外向き通信の制御はリソースを作る段階でパブリックIPを持たせない、ルーティングの段階でデフォルトルートを引かない、許可ルールの段階でプロキシの許可リストに絞るという3つの独立した層に分けて設計し、通信要件の異なるタスクの種類ごとに専用のサブネットを割り当てることで、送信元サブネットと許可ホスト名の対応が把握しやすい形にしている。一方でニュース収集を行うタスクだけは、参照先の外部URLが動的で事前に列挙できないため、静的な許可リストでは絞り込めない課題が残っており、既知の悪性ドメインを拒否する方式など別のアプローチを今後検討するとしている。

出典: https://zenn.dev/yook/articles/aws-egress-allowlist-without-network-firewall

## 7. Claude Codeのコンテキスト引き継ぎを205セッション運用したら、申し送りが誤りを増幅していた

aiqlabsさんの記事。著者はClaude Codeを1つのプロジェクトで76日間走らせ続け、205セッション分のログを残しているが、セッションをまたいで文脈を引き継ぐ仕組みを導入した後、引き継ぎファイルが誤りを増幅させる問題に気づいたという。ある調査で「改名は検索索引を壊す」という結論が申し送りに残ったが、実際には測定コード自体の不具合が原因で、次のセッションはその結論を前提として改名という選択肢を検討から外してしまった。測定方法やサンプル数が記録されていなかったため、後から疑う手がかりも残っていなかった。また「現在20本公開中」のような時点の状態を書くと、次のセッションはそれを現在の値として信じ込み、8日後の検証では実際の件数が32本に増えていたことも判明している。さらに長いセッションで生じたツール呼び出しの破損ログが申し送りを通じて次のセッションに持ち越され、新たな破損を生む手本になってしまうパターンも見つかった。これらを踏まえ著者は、測定値には測り方とサンプル数と日付を必ず書く、重要な判断の前には数値を再測定する、機械で読める事実は申し送りの散文ではなくスクリプトとして残すという3つのルールを導入し、暫定的な観測が確定した前提として一人歩きしないようにしている。

出典: https://zenn.dev/aiqlabs/articles/70370e973d8425

## 8. Claude Code の権限確認をスキップする前に置いた7つのフック — 75日運用して踏んだ事故の記録

aiqlabsさんの記事。著者はClaude Codeを毎日の業務で75日間、権限確認をほぼ出さない設定で走らせ、その間に公開済みの自動化ツールを22本出荷した一方で、実際に何度か事故も踏んでいる。作業中のファイルを一時ファイルと誤認して削除されたことをきっかけに、あらゆる削除系コマンドを検出し、パスやファイル名パターンなど複数条件を満たしたときだけ実行を許可する承認トークンの仕組みを導入した。catでの読み出しは防げてもbase64やxxdを経由した迂回読み出しが残っていたため、機密パスと読み取り系コマンドの組み合わせを正規表現で監視するフックも追加している。既存のスキル名から「隣接領域らしい名前」を合成し、実在しないスキル名をドキュメントに書いてしまったこともあり、Edit・Writeの操作からスキル名らしき文字列を抜き出して実在を確認し、架空のものであれば実行をブロックする仕組みも用意した。もっとも厄介だったのは、長いセッションの終盤で「8ファイル作成しました」と報告されたのに実際のツール呼び出しログにはWriteが1件もなかったケースで、これは観測できない部分をあるべき結果で埋めてしまう現象であり、フック単体では根本的に防げないと著者は率直に認めている。そのためmalformedなエラーが2回累積した時点でセッションを即座に終了させる撤退基準を設け、壊れたログを次のセッションが読み込まないように機械的にサニタイズする仕組みで対処した。あわせて、毎回のyes/no確認では承認が機械的になり実質ノーガードになってしまうこと、エラーメッセージに次の承認コマンドをそのまま書くとサブエージェント自身がそれを実行してガードを迂回してしまうことなど、フック設計そのものに潜む落とし穴も具体的に記録している。

出典: https://zenn.dev/aiqlabs/articles/2494e9a5abf58d

## 9. VPNを自前で建てたら、商用VPNが月400円で成立する理由が分かった

gyugyu86さんの記事。公衆Wi-Fiでの通信を暗号化したくて月400円ほどの商用VPNを検討していた著者は、契約前に、自分の全通信をその事業者に預けることになるのに中身を確認する手段がないことに引っかかりを覚え、まずAWSのEC2にWireGuardを自前で構築してVPNの仕組みを理解することにした。実際にやってみるとWireGuardの設定は30分程度で終わり、トンネルと呼ばれる仕組みの実体はアドレスの書き換えと転送の許可という基本的な処理に過ぎないことが分かったという。構築後に課金の内訳を分析したところ、AWSの料金は通信量ではなく主に稼働時間で決まり、データ転送は月100GBまで無料であることも判明した。そのうえで著者は、AWSの従量課金がおよそ1GBあたり0.1ドルなのに対し、専用サーバー事業者は1GBあたり0.005ドル以下で帯域を調達できるという20倍から40倍の差に気づき、この帯域調達コストの構造的な差こそが商用VPNを月400円で成立させている正体だと結論づけている。自前のVPNが割に合うのはあくまで個人利用の範囲にとどまり、商用VPNの低価格は単なる企業努力ではなく調達構造の違いによるものだという。

出典: https://zenn.dev/gyugyu86/articles/7c3c9178b85d63

## 10. Graph Engineeringの外側で、AIエージェントのPRは衝突する

veripsaさんの記事。AIエージェントのシステムをノードとエッジと状態と遷移として設計するGraph Engineeringという考え方は、LangChainやGoogle ADK、Microsoft AutoGenといった主要フレームワークが採用しており、エージェント内部のワークフロー制御には優れている。しかし著者は、複数のエージェントが並列でコードを変更する際に実際に問題が起きる場所は、この実行グラフの内側ではなく外側だと指摘する。同じ関数や設定を別々のエージェントが変更していたり、どちらのPRを先にマージするかで結果が変わってしまったりする競合は、個々のエージェントの実行グラフには存在せず、PRとPRの関係というグラフが見ていない領域で発生するというのがその核心である。そこで著者は、タスク完了までのエージェント内部のフローを扱う実行グラフと、複数の変更の関係や着地の判断を扱う調整グラフという二層構造が必要だと主張する。前者はエージェントフレームワークが担うのが自然だが、後者はGitHub上で複数のエージェントや人間が共有する情報として持たれるべきだとしている。著者が開発しているVeripsa Coreは、Graph Engineeringそのものを置き換えるのではなく、複数のエージェントと人間が同時に開いているPRのあいだに共有される調整コンテキストを提供することで、この外側の衝突を管理しようとする取り組みとして位置づけられている。

出典: https://zenn.dev/veripsa/articles/graph-engineering-ai-pr-coordination
