## 1. タイムアウトは「いつ諦めるか」を決めるだけ、誰にWorkerを使わせるかは決めない

1つのWorkerプールを複数の外部サービスで共有しているとき、そのうち1つがエラーも返さずに黙り込むと何が起きるか。筆者はこれを、仮想時間で動く決定的なGoのシミュレーションで比べた。Workerは20本、依存先AとBにそれぞれ毎秒200件が届く。Aは常に20ミリ秒で成功し、Bは10秒間ずっと応答しない。Bが正常なら数本で足りる負荷だが、Bの1件が2秒間Workerを握るので、空いたWorkerはすべてBの待ち行列に吸い込まれる。結果、タイムアウトだけではAは2000件中100件しか終わらなかった。タイムアウトを10分の1の200ミリ秒に縮めても914件にとどまった。Bに届く量が、Workerが処理できる量をまだ上回っているからだ。連続失敗で遮断するサーキットブレーカーを足すと、Aはほぼ全件まで戻る。ただ最初の2秒は、Workerが全部Bに張り付いて失敗が揃うのを待つので、そのあいだAも止まる。一方、Bが同時に使えるWorkerを4本までに絞る、いわゆるバルクヘッドにすると、Aの待ち時間は最初から平常時と同じ20ミリ秒のままだった。代わりにBの側には2000件近い滞留が積もる。その滞留をどこへ逃がすかを決めないと、今度はメモリやキューが際限なく膨らむ。バルクヘッドとブレーカーを併用すると、Aを守りつつBの滞留も退避できた。筆者の整理は、相手が遅いならバルクヘッド、相手が即座に落ちるならブレーカー、両方ありうるなら併用で、滞留の行き先まで設計する、というものだ。Workerを増やす案は、この条件だと400本必要になり、次にもっと長く黙られたら破綻するので捨てている。退避したジョブの戻し方や、複数のPodでブレーカーの状態を共有する話、即エラーのケースでの立ち上がりは検証していない、と明記している。

## 2. 「修正待ち」は配布物ではなく、カーネルの系列ごとに見る

深刻度の高いカーネルのTCP脆弱性が騒がれた週の話だ。筆者がAmazon Linux 2023の本番サーバーの状況を確認すると、既定のカーネル、つまり6.1系は修正待ちだった。ところが別パッケージとして提供されている6.12系には、修正済みのセキュリティ勧告がすでに出ていた。同じOSの中で、系列によって修正の有無が分かれていたわけだ。筆者は6.1系を待たず、系列ごと6.12へ乗り換えた。ここに落とし穴が3つあった。1つ目は、二つの系列はパッケージ名が違うので、dnf updateをいくら打っても6.1系の最新に上がるだけだということ。更新しているのに警告が消えない理由はこれだった。乗り換えは、6.12系を明示的にインストールしたときにしか起きない。2つ目は、起動するカーネルを切り替えただけで満足すると、次の更新で既定が6.1系に戻りうること。今日切り替えることと、今後も6.12系を追いかけることは、別の設定ファイルで決まっている。3つ目は、起動に失敗したときの戻り先として6.1系を消さずに残したことの代償だ。使っていない系列にも更新が届くので、再起動が必要だという警告が出続ける。実際に動いている系列かどうかを確かめてから判断している。本番の再起動はメンテナンス画面を出し、裏口から実際のページを確かめてから開ける手順を毎回なぞっており、止まっていたのは21秒だった。同じ週に見ていたUbuntuのサーバーは、使っている系列に修正が出ておらず待つしかなかった。筆者は、脆弱性対応の半分は、追跡表の中で自分のサーバーがどの行に当たるかを探す作業だと締めている。行が違えば、打てる手も締め切りも変わる。

## 3. GitHub ActionsからAWSに入るロールを、使い捨てのブランチから使えなくする

11月12日、乗っ取られた約4800のGitHubアカウントを使って、Actionsのシークレットやクラウドの認証情報が盗まれたと報じられた。手口は、書き込めるリポジトリに使い捨てのブランチを作って認証情報を集めるワークフローを仕込み、GitHubのOIDCトークンをAWSの一時認証情報に替え、長期のアクセスキーまで作ってから痕跡を消す、というものだ。筆者は、この経路がどこで塞がるかを自社のAWSとGitHubで試した。信頼する範囲だけを変えたロールを3つ用意し、mainへのpush、使い捨てブランチへのpush、そこからのPRの3通りで動かす。組織全体を信頼するロールは、3通りとも引き受けられた。組織のどこか1つのリポジトリに書き込めるアカウントが乗っ取られれば、どのブランチからでも使えるということだ。IAMコンソールでリポジトリとブランチを空欄のまま作ると、この広い設定になる。このリポジトリのmainだけを完全一致で信頼するロールは、使い捨てブランチとPRからは拒否された。さらにGitHubのEnvironmentでデプロイ先をmainに限ると、使い捨てブランチからのジョブはトークンが出る前にGitHub側で止まった。筆者が気づいた点がもう1つある。7月中旬以降に作ったリポジトリでは、トークンの中のリポジトリ表記が数字のIDを含む形に変わっており、ネットでよく見る書き方の条件だと一致しない。条件を書く前に、実際の値を一度見ておくのが確実だという。ただし、この絞り込みはどれも、mainから動いたジョブなら通す。Freeプランの非公開リポジトリではブランチ保護も必須レビュアーも作れず、書き込める人ならmainへ直接pushできてしまった。だから、入られたあとに長期のキーを作らせないよう、ロールの権限そのものも絞っておく。実際に、読み取りだけを許したロールでは、IAMユーザーの作成は拒否された。

## 4. 宛先を替えたら88ターン動いた、それでも乗り換えなかった

筆者は、ECサイトの脆弱性をAIエージェントに診断させ、承認を得て直すプラグインを作っている。1回の診断はClaude Opus 5.5と40から90ターンやりとりし、ある晩の実例では20分で7ドルあまりかかった。バージョンごとに毎晩回すには高い。そこで、月に一定回数まで無料で使える、さくらのAI Engineに向けてみた。Anthropic互換の窓口があるので、SDKのまま接続先を替えるだけで呼べる。プロンプトキャッシュやサーバー側のWeb検索などは外し、文脈があふれないよう古いツール結果を短い札に置き換える処理を足した。Kimi系のモデルで流すと、88ターンのあいだツール呼び出しの形を一度も崩さず、わざと仕込んだ「番号を変えると他人の注文が見える」不具合も見つけた。ここまで動くとは思っていなかった、と筆者は書く。ところが、別のバージョンのショップで2つの穴が見えた。1つは、ガードに2回断られた更新の提案を、最終レポートで「提案した」と書いたことだ。店主はありもしない承認ボタンを探すことになる。同じ状況で、Claudeの2モデルはできなかったと書いた。もう1つは、61ターン目にサーバー側から400エラーが返り、16分の作業がレポートなしで消えたことだ。値段の計算でも意外な結果が出た。エージェントは毎ターン会話を全部送り直すので、キャッシュ読みが入力の20分の1になるOpusと違い、キャッシュ割引の書かれていない有料の単価で計算すると、88ターン分はOpusとほぼ同じ額になった。Haiku 5.5も試したが、長いプロンプトでは単価が上がる料金表とターン数の多さで、思ったほど安くならなかった。筆者は乗り換えないと決めた。効くのはモデルの単価よりも、キャッシュが効くかと何ターンで終わるかで、エージェントの仕事はツールを呼べることではなく、できなかったことをできなかったと書けることだ、とまとめている。無料の試行で、自分たちのコンテナ側の不具合が2つ見つかったのは収穫だったという。

## 5. AIが書く前提のアーキテクチャは、選択肢を減らして機械で止める

ここからはAIとの付き合い方の話を2本です。5本目は、コードの大半をClaude Codeに書かせている学生エンジニアが、アーキテクチャの考え方をどう変えたかを書いた記事です。筆者が挙げるAIの性質は3つ。周りのコードを真似るので、書き方が2通りあれば間違ったほうも増える。判断の分岐が多いほど答えがぶれる。書く量が多く、人のレビューでは追いつかないが、エラーを読んで直すのは得意だ。そこで筆者は、アーキテクチャの目的を、選択肢を減らすことと、決めたことを機械で止めることの2つに置き直した。層は入口、業務の処理、データの3つまでに限り、依存は一方向だけにする。入口の処理は、権限を確かめる、入力を受け取る、業務の処理を呼ぶ、応答を返す、の4手だけにそろえる。状態を変えるもの、読むもの、外と通信するもので名前の型を決め、保存の前後で自動に動くフックのような見えない呼び出しに業務の処理を隠さない。そのうえで、フォルダごとに使ってはいけない部品を静的解析で禁止する。一番効いたのは、検査のエラーメッセージに、何が駄目かだけでなくどこに書けばよいかと、規約のどの節かまで書いたことだという。AIはそのまま修正の指示として読んで直す。抑制コメントで黙らせるとAIがそれを直し方として真似るので、合わないと思ったら先に規約を直す、と決めた。途中から入れる規約は、既存の違反を一覧に凍結し、件数が1つでも増えたらCIで落とす形にして、少しずつゼロまで減らした。機械で判定できない名前と役割の一致などは、実装の経緯を知らない別のエージェントに規約と差分だけを渡して見せる。筆者は、大事なのはきれいな層の分け方より、AIが迷わないことと、間違えたら機械が止めることだと結んでいる。

出典: https://zenn.dev/yu_uya_h/articles/ai-era-architecture

## 6. Agent SkillsがLinux Foundation傘下へ、手持ちの27スキルを仕様で検査した

最後は話題のニュースです。10月22日、AnthropicはAgent Skillsの仕様を、Linux Foundation傘下のAgentic AI Foundationに寄贈しました。MCPに続く2つ目の寄贈です。この記事は、その発表を整理したうえで、筆者が自分のスキルを仕様に照らして検査した記録です。寄贈されたのは仕様、名称とロゴ、GitHubの組織、公式サイトのドメインで、メンテナはAnthropic、Google、OpenAIなどのエンジニアが個人の立場で務める。当面の計画は、バージョン付きのリリース、正式な提案の手続き、スキルを書く人と入れる人向けのセキュリティ指針の3つで、仕様そのものはまだ変わっていない。仕様で必須なのは、ディレクトリ名と一致する名前と、何をしていつ使うかを書いた説明文の2つだけだ。エージェントが起動時に読むのもこの2つなので、自動で呼ばれるかどうかは説明文の質で決まる。筆者は公式の検証コードを読んで同じ判定をする小さなスクリプトを書き、4つの個人リポジトリにある27個のスキルを検査した。不合格は6個で、理由はすべて、先頭のメタデータ欄がないことだった。Claude Codeは寛容で、欄がなければ本文の最初の行を説明文として使う。そのため見出しだけのスキルでは、名前と説明が同じ文字列になっていた。すぐ下に立派な説明の段落があるのに、エージェントには届いていなかったわけだ。明示的に呼ぶ運用だったので実害は出ていなかったが、記事を書いてと頼んだときに自分で選ばれるかは名前頼みだった。一方、claude.aiへのアップロードやSkills APIでは、仕様にない欄があるとエラーになる。同じスキルを外へ持ち出すなら、名前と説明文を必ず書き、独自の欄は使わないのが無難だという。スキルを、エージェント向けの手順書と、バッチがシステムプロンプトとして読む文書の両方に使い回している場合は、形式の変更がそちらにも波及する点にも触れている。
