## 1. ローカルAI GatewayにResource Controlを実装した

hisa_tech_2973さんの記事。以前実装したExecution Controlは、LLMのツール呼び出しをallowlistで判定し「何を実行してよいか」を制御するものだったが、それだけでは`git add ../other-service/config.yaml`のようにWorkspaceの外にあるファイルを対象にした操作を防げないという課題が残っていた。今回はその隙間を埋めるため、操作ごとに対象パスを抜き出すExtractor層、相対パスと絶対パスをWorkspaceのルート基準に正規化するResolver層、正規化後のパスがWorkspace内かどうかを判定するPolicy層という3層構成を追加した。`--`区切りのないgit diffのように対象パスの見分けが難しいコマンドでは、非オプション引数を機械的にすべてパス候補として扱うことでフェイルセーフを優先し、パス比較も文字列の前方一致ではなく相対パス計算で境界を正確に見る実装にしている。複数の対象リソースのうち1つでもWorkspace外と判定されれば操作全体を拒否する設計で、「何を実行するか」の制御に「どこまで実行してよいか」という範囲の制御を重ねた形になっている。

## 2. AIエージェントにCMSのメディアを運用させる ― 画像のバイト列はLLMに通さない

pikonoriさんの記事。AIエージェントにブログ記事の執筆だけでなく、アイキャッチなど掲載画像のアップロードまで任せようとしたときに直面した問題を扱った記事。1MBの画像はBase64に変換すると1.3MBほどの文字列になり、それをそのままLLMのコンテキストに渡すとトークンを大量に消費してしまう。そこで著者が開発するヘッドレスCMS Tesseraでは、投入経路を役割ごとに2つに分けた。小さいファイルやテキストはMCPの`upload_asset`でBase64のまま約5MBまで扱い、大きな画像や動画はHTTPの`/api/assets`エンドポイントへAPIキー付きのmultipartでcurl送信し、返ってきたURLを記事に差し込む方式にすることで、大きなバイト列そのものはLLMのコンテキストを経由しないようにしている。「何をLLMに通し、何を迂回させるか」という線引きを最初に決めたことが、実運用に耐える設計につながったという内容だった。

出典: https://zenn.dev/pikonori/articles/ai-agent-media

## 4. エージェントは「差分の外」を読む：ADK for Go でAIレビューを作り直した実践

snknskさんの記事。Gitの差分をGeminiに渡して構造化JSONでレビュー結果を受け取る、呼び出し1回だけの単純なレビューツールを半年運用してきた著者が、それをADK for Goのエージェントループへ作り直した記録。単発呼び出しの限界は、差分だけでは判断できない「設定資料と矛盾する変更」を拾えないことで、小説原稿でのテストでは単発呼び出しが文章密度の指摘に留まったのに対し、エージェント版は設定ファイルを自分で開きに行き、矛盾を3件「Blocker」として指摘できたという。実装では既存の差分専用インターフェースを壊さず新しいWorkspace対応の型を並行実装したほか、差分取得後にチェックアウトしないとエージェントが古いリビジョンのファイルを読んでしまう落とし穴や、停止条件を実行時間ではなくツール呼び出し回数で区切り上限到達時もエラーではなく打ち切りとして扱う工夫、作業ディレクトリを読み取り専用にしつつシンボリックリンク経由のパストラバーサルを防ぐ対策などを積み重ねている。単発呼び出しからの移行で古いMarkdown形式の指示がプロンプトに残っていたことにも触れ、プロンプトもコードと同様にリファクタリング対象として扱うべきだと述べている。

## 7. サーバーレスDB×Lambdaで大量接続時にタイムアウト発生。スケールアップせずAPI Gatewayキャッシュで解決した話

suekichi_systemさんの記事。従量課金のサーバーレスDBをLambda・API Gateway構成のバックエンドで使っていると、アクセスが集中したタイミングでLambda実行環境が同時多発的に立ち上がり、DBの同時接続数上限に達してタイムアウトが起きることがある。真っ先に思いつく対策はLambdaのメモリ増強やDBクラスタのスケールアップだが、これはランニングコストが増える割に「重複したアクセスが多い」という根本原因を解決できない。著者はAPI Gatewayのキャッシュ機能を使い、同じ条件のリクエストへの重複したDB問い合わせ自体を減らすことで接続数を根本から抑える方向を選んだ。ステージ単位でキャッシュを有効化し、キャッシュキーとして使うパラメータを設計したうえで、マスタデータのように更新頻度が低いものは長め、更新が頻繁なものは短めとTTLを使い分け、最大でも3600秒に収めている。REST APIでしか使えずHTTP API v2では非対応であること、レスポンスサイズが1MBまでという制約があること、ユーザーごとに異なるデータはキャッシュ対象から除外する必要があることにも触れており、0.5GBからの低コストで、一部エンドポイントだけの部分導入でも効果が出るとまとめている。

## 8. WebRTC SFUをCloud RunではなくCompute Engineに構築した理由

ym_studio_craftさんの記事。カメラ映像を複数人へリアルタイム配信する個人開発サービスで、映像をデコードせずそのまま転送する軽量なSFU(Selective Forwarding Unit)をGoで実装するにあたり、最初はサーバーレスで運用が楽なCloud Runを検討していたが、最終的にCompute Engineに落ち着いた経緯を扱った記事。WebRTCは通信確立にICEを使い、メディアは任意のUDPポート上でやり取りされるが、Cloud Runはコンテナへの外部トラフィックをHTTP(S)やgRPCとしてのみプロキシする設計のため、任意のUDPポートを公開できないという構造的な制約に突き当たったという。Compute EngineのVM上にGoバイナリをsystemdサービスとして常駐させ、ファイアウォールでは50000〜50100番のUDPポート範囲だけを開放し、pion WebRTCライブラリの`SetEphemeralUDPPortRange()`でICEに使うポートをその範囲に固定することで、ローカル開発と同じバイナリをそのまま本番で動かせる構成にしている。実行中のバイナリへ直接scpで上書きしようとするとLinuxがファイルへの書き込みを拒否する「ETXTBSY」エラーに遭遇した運用上の発見も紹介しており、VMの起動・監視・パッチ適用やスケールアウト時の負荷分散設計といった責任を引き受ける代わりに、通信要件そのものによってインフラの選択肢が絞られたと結論づけている。

出典: https://zenn.dev/ym_studio_craft/articles/79a04250e13044

## 9. GitHub ActionsのGoテストを8分→3分弱に短縮 —— setup-goのキャッシュ共有を見直す

remitaidさんの記事。Goをバックエンドに採用しているRemitAidで、ユニットテスト・DBインテグレーションテスト・E2Eテストの3種を含むCIジョブが10分のタイムアウトを頻繁に超える問題への対処を扱った記事。当初はDBのI/Oを疑ったが、実際のボトルネックはコンパイル時間だった。原因は`actions/setup-go`が内蔵するキャッシュのキーが「OS・Goのバージョン・go.sum」だけで自動的に決まる仕様にあり、同じリポジトリのlintジョブとテストジョブが同じキーを取り合ってしまい、テストジョブ側のコンパイル結果がキャッシュに残らない状態が続いていた。対策として、ジョブごとに固有の接頭辞を付けてキャッシュキーを分離したうえで、サイズがほぼ変わらないモジュールキャッシュと、コミットのたびに増分するビルドキャッシュを別々に管理し、ビルドキャッシュのキーには直近のコミットハッシュを含めてrestore-keysで段階的にフォールバックできるようにした。この見直しにより合計時間は8分から2分55秒に、ユニットテストは2分58秒から20秒に、E2Eテストは3分26秒から38秒に縮まったという。複数ジョブでキャッシュを共有する際は明示的に分離しないと、キャッシュが実質機能しなくなるという教訓が印象的だった。

出典: https://zenn.dev/remitaid/articles/fa94cb567f5d1d

## 10. encoding/json/v2 に至る14年

ymotongpooさんの本。Go 1.0から存在するencoding/jsonパッケージが、フィールド名の大文字小文字を区別しない一致のような既知の問題を14年間抱え続けてきた経緯と、Go 1.27で正式化されたencoding/json/v2に至るまでの道のりを、issueや提案、Gerritの変更、標準ライブラリのソースを追いながら整理した10章構成の一冊。標準ライブラリの互換性維持がなぜこれほど長く問題を放置させたのか、コミュニティがその間どう回避策で凌いできたのか、根本的な再設計の議論がどう始まりGitHub issueから正式な提案へ育っていったのか、v1との互換性を保ちながらv2をどう組み込んだのかという実装方式まで、約56,000字をかけて丹念に追っている。1つのAPI変更がどれほど長い合意形成と検証を経て言語の標準に組み込まれるかを追体験できる内容で、目先の機能追加のニュースだけでは見えない、標準ライブラリの設計判断の重みを感じさせる記事だった。

出典: https://zenn.dev/ymotongpoo/books/go-json-v2-history
