## 1. AIにPR作成を任せたら、レビュー負荷が上がった話

## 3. Claude Code の CLAUDE.md に何を書くと効くのか(1年運用した実測)

nyacoaiさんの記事。Web制作を本業としながら1年間毎日Claude Codeを使い続けてきた著者が、CLAUDE.mdの書き方によって出力の安定度が大きく変わることに気づき、その知見をまとめている。効くのは「モダンな感じで」のような好みの指示ではなく禁止事項だという逆転の発見が核心で、好みの指示は解釈の幅が広すぎて長い作業の後半で崩れやすいのに対し、これをするなという禁止は判定が機械的なぶん崩れにくいと説明する。具体的には、CSSの直書きを避けるといった判定が明確なルールを書くことで出力のブレを抑え、表記ゆれや命名規則、コンポーネント粒度などプロジェクト固有の決定を先に固定しておくことでAIが迷わなくなるとしている。さらに、情報が足りないときは勝手に埋めず要確認の印をつけて止まるといった分岐点の扱い方を事前に明示し、詳細な規約は別ファイルに逃がしてCLAUDE.md本体は案件固有の前提に絞ることで安定性が増すという。最大の効果は同じ指示を繰り返す回数が減り、手戻りの往復が減ったことだと結論づけている。

## 4. テスト環境のない本番APIで誤発注を封じ込める設計

ozaponさんの記事。GMOコインのFX APIにはサンドボックスもテスト環境も存在せず、開発中のコードがそのまま本番口座に作用してしまうという制約の中で、AWS Lambda上のPython自動売買システムをどう安全に作るかを扱った記事。著者が採用したのは、独立した2つの環境変数が両方揃わない限り発注系のPOSTを送らせない仕組みで、フラグとフェーズ識別子のどちらもデフォルトは禁止側にしてあるため、片方の設定を誤っても発注には至らない。ところが実際には、バッチ層と非常停止機能がそれぞれ独自に判定ロジックを書いてしまっていたことが後から発覚する。インフラが供給する値は小文字表記だったにもかかわらず、バッチ層は大文字との厳密一致で判定していたため常に遮断される一方、非常停止機能は大文字小文字を無視する実装だったため解禁状態と誤判定してしまい、発注は止まっているのに非常停止だけが誤作動するという危険な状態を招いていたという。著者はこの経験から、安全機構を層として重ねることと判定ロジックを複製することはまったく別物だと結論づけ、修正では判定を単一関数に集約したうえで、値の一致ではなくオブジェクトの同一性をテストで保証することで、誰かが再び独自の判定を書いてしまう事態を検知できるようにしている。

出典: https://zenn.dev/ozapon/articles/gmo-fx-order-containment

## 5. AWS RDSの高負荷をスロークエリチューニングせずに解消させた事例

peipeiさんの記事。SaaSで夜間バッチ実行中にAWS RDSのCPU使用率が高騰する事象に対し、著者は最初スロークエリを疑い、一覧画面のソート用カラムを更新するバッチ処理のOR条件による非効率なクエリが原因だと考えて正規化・別テーブル切り出しを行ったが、CPU使用率は75%から55%程度への改善にとどまり、通常時の2倍以上のままだった。CloudWatchデータベースインサイトで改めて分析したところ、問題は個々のクエリの実行時間ではなく実行回数の突出した多さにあることが判明する。真犯人は、Rundeckのシェルスクリプトが全テナントを10分割し、バックグラウンド実行で同時並行処理していたことによる、同一クエリの大量同時実行だった。対策として並列実行そのものをやめ、10並列を7分割にしたうえで週1回に全並列実行していたものを週7回、日別に1シャードずつという分散スケジュールへ変更し、同時にDBへ接続するバッチプロセスを常に1つだけにしたところ、CPU使用率は60〜70%程度から10%以下まで下がったという。スロークエリのチューニングではなく、並列度そのものを見直すことが真の解決策だったという事例。

出典: https://zenn.dev/peipei/articles/2458661c7cdb81

## 6. 個人開発だからと管理者権限を日常使いしていた反省から、AWSの権限運用を見直した話

yookさんの記事。個人開発のサービスをAWSで運用する中で、セッション乗っ取り時の被害を抑える発想から自分の権限設定を見直した記録。IAM Identity Centerでのログイン自体は整えていたものの、日常の調査もTerraformのapplyも本番のコンテナ入れ替えも、すべて一番強い管理者権限のセッションで済ませていたことに気づき、これを改めている。CI用にterraform-plan、terraform-apply、app-push、app-rolloutといった複数のロールがすでに定義されていたにもかかわらず活用できていなかった点を反省し、人間もこれらのロールを共用する運用へ転換した。通常ユーザーからデプロイ用ロールへはAssumeRoleで一時的に権限を委譲する構成とし、呼び出し元のPermission Setでの許可とロール側のTrust Policyでの信頼元制限という二重の定義が揃わないと切り替えが成立しないようにしている。さらに、シークレットの読み取りや特定のIAM変更を明示的なDenyで絶対に禁止したうえで必要な操作だけをAllowリストで許可するfail-closed設計を徹底し、同一のSSOセッション内では権限委譲のリスクが残ることから、read・deploy・adminの3ユーザーを完全に分離して運用することで、作業ごとの最小権限化とセッション単位での被害限定を両立させている。

出典: https://zenn.dev/yook/articles/aws-deploy-role-separation-fail-closed

## 7. Cloud Runで1つのイメージをweb/workerに分け、権限と設定を絞る

snknskさんの記事。Cloud Run + Cloud Tasksで非同期処理を組む際、最初はWeb UIとタスク受付口を同じサービスの同じルーターに同居させがちだが、その構成ではタスクの受付口が公開サービス上に存在し続けてしまい、防御がアプリ内のOIDC検証ミドルウェア1枚だけに頼ることになるという弱点を抱える。著者はこの弱点を潰すため、同じコンテナイメージを環境変数で切り替えつつ、web用とworker用という2つのCloud Runサービスとしてデプロイし直している。webとworkerにはそれぞれ別々のサービスアカウントを割り当て、依存性注入の段階でworkerロールはAIクライアントや通知、Cloud Tasksクライアントを組み立てず、逆にwebロールはタスク検証ミドルウェアやワーカーハンドラを組み立てないようにすることで、担当しない機能に必要なシークレットへのアクセス権そのものを持たせない設計にしている。workerサービスには未認証アクセスを許さない設定を施し、Cloud Tasksの実行用サービスアカウントにだけ起動権限を付与することで、未認証リクエストにアプリが応答する余地を完全に消している。結果として、CPUやメモリ、同時実行数といったスペックをwebとworkerでそれぞれの特性に合わせて独立に設定できるようになり、どちらが遅いのかという障害切り分けも容易になったという。

出典: https://zenn.dev/snknsk/articles/cloudrun-web-worker-split

## 8. MCPサーバーをuvxで動かしている人は、一度du -sh ~/.cache/uvを叩いてみてほしい

canlyさんの記事。社内で使っているClaude Codeのプラグインがローカルストレージを圧迫しているという相談をきっかけに調べたところ、`~/.cache/uv`が70GBにまで膨れ上がっており、その半分以上がMCPサーバー2つ分のキャッシュだったことが判明したという。詳しく追うと、MCPサーバー用の仮想環境が500以上蓄積しており、セッションを起動するたびに数個ずつ増えていく傾向が見られ、ランチャーの種類や終了方法とは無関係に発生していた。著者は設定を1つずつ機械的に変更しながらA/Bテストで犯人を絞り込み、パッケージのバージョンを最新指定にしていると環境が増え続け、バージョンを固定すると増加が止まることを突き止めている。原因はuv内部の実装上の問題で、最新指定が内部的にはキャッシュ無視の指定と同じ扱いになり、実行のたびに環境をまるごと作り直していたことにあった。この不具合はuvの新しいバージョンで修正済みだが、それより前のバージョンを使っている場合の暫定対応としては、従来のキャッシュ削除コマンドではわずかしか削減できないのに対し、整理用の別コマンドを使えば大半の容量を削減できたという。バージョン指定に切り替えることでも根本的に回避できる。

出典: https://zenn.dev/canly/articles/03e1086f6b6056

## 9. SageMakerのCPU推論が想定の3倍遅かった話

dgtechさんの記事。Digital GarageがOCR機能で使っているLayoutLMv3ベースの機械学習モデルの推論が、想定の1000ms、手元のM2 Macでの700msに対し、SageMaker上のエンドポイントでは約3000msもかかるという異常事態に遭遇し、その原因を突き止めた記録。1つ目の原因は相対位置バイアス処理にあり、約300万要素を取り出すgather操作で、推論エンジンが最適化されたカーネルではなく低速なリファレンス実装を使ってしまっており、これだけで全体の4割ほどを占めていた。著者はこのインデックス操作をone-hot変換によって行列積に書き換えることで大幅に短縮し、さらにモデルの入出力形状を固定シェイプにすることで動的シェイプ推論のオーバーヘッドも削減している。2つ目の原因は、使用していたインスタンスがAMX命令セットを搭載しているにもかかわらず、OSのカーネルが古くAMXの使用許可要求に対応しておらず機能を活かせていなかったことで、公式にはCPU向けの新しいAMIが未提供だったため、GPU版のAMIをあえてCPUインスタンスに指定してカーネルを引き上げるという回避策をとり、該当処理の時間を大幅に短縮している。両施策を合わせた結果、推論時間は最初の3200msから約769msへと約75%改善し、精度低下やコスト増なしに目標の1000msを達成したという。

出典: https://zenn.dev/dgtech/articles/f56c05c8975dfa

## 10. Goの名前付き戻り値と明示的な戻り値をベンチマークで比較する
