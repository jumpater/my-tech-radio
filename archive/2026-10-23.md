# tech-radio 2026-10-23

## オープニング

tech-radio、2026年10月23日分です。今日は全部で5本をお届けします。テーマは、「任せる相手に、どこまで渡すか」です。AIエージェントに渡す認証情報、MCPで任せる読み取り権限、サブエージェントの完了報告。そして、本番のデータベースに負荷をかけずに数億件を消す運用と、偽の環境に居座った攻撃者の観察記録。どれも、渡す範囲と確かめ方が設計の中身になっている記事です。最後に、注目の新規リリースを一つ添えます。

## 1. 「.envを出力しないで」は対策ではない

sscodeaiさんの記事。AIエージェントに本番の認証情報を渡すとき、多くの現場は.envを読ませたうえで、指示文に「中身をそのまま出力しないこと」と書く。筆者はこれを対策ではないと言い切る。指示文はアクセス制御ではなく、エージェントはプロンプトインジェクションで乗っ取られることもあれば、うっかり中身を表示することもあるからだ。一度コンテキストに入った値は、履歴やログやコミットに残り、あとから消しても取り消せない。そこで筆者は、秘密を「渡す」のをやめて「使わせる」形にする権限設計を整理している。事故が起きる前提で、値そのものをエージェントの手元に置かない、という考え方だ。

出典: https://zenn.dev/sscodeai/articles/agent-secret-access-design

## 2. 「読むだけ」と頼んだMCP接続は、本当に読むだけか

build_anotherme さんの記事。社内の案件一覧をAIに読ませて状況をまとめてもらうとき、「更新はせず、読むだけで」と伝えてMCPで接続したとする。その接続が本当に読み取り専用かどうかは、何を見れば分かるのか。筆者の出発点は、AIへの指示に頼らず、接続に使うアカウントや認証情報の権限を先に絞ることだ。そのうえで、ツール一覧に何が表示されるかと、実際に操作を実行できる権限とは別の話なので、分けて確かめる方法を整理している。業務のAPIやデータにMCPをつなぐ人にとって、「読むだけ」の約束をどこで検証するかの手がかりになる。

出典: https://zenn.dev/build_anotherme/articles/8f55b8f9d0f7fa

## 3. 「完了しました」を信じない、サブエージェントの報告設計

sitio1さんの記事。作業を委譲した親が観測できるのは、返ってきた報告のテキストだけだ。そこに「完了」と書いてあっても、実体と食い違っていることに、報告を読むだけでは気づけない。実際に、進捗記録は完了なのに生成物がどこにも存在しない、という乖離が起きたという。そこで筆者は、確認した証跡のパスを報告の書式に入れる、検証ツールが0件を返したときに完了と読み替えない、縮小して実装した部分は列挙させて採否は人間が決める、完了条件をチェックリストとして固定する、といった対策を足していった。いずれも、実際に乖離が起きたあとに追加した決まりだという点に説得力がある。

出典: https://zenn.dev/sitio1/articles/781f782927d6c3

## 4. 数億件のテーブルから、本番を止めずに少しずつ消す

日本トレカセンターの小林さんの記事。役目を終えたデータを、数億件規模のテーブルから、通常のリクエストを受けているのと同じMySQLに対して消す話だ。インデックスで絞れない対象なので、一度に消すと本番への影響が心配になる。筆者のチームは、対象の抽出と削除を分けた。削除対象のIDをAmazon S3に分割して保存し、Goのバッチが少量ずつ削除する。実行量を制限しながら、複数回の実行で終わらせる設計だ。実行基盤としてS3 Batch OperationsとStep Functionsも検討したと書かれていて、選択肢を比べた経緯も読める。大量削除を迫られたときの、現実的な進め方の見本になる。

出典: https://zenn.dev/jtcc/articles/s3-manifest-chunked-cleanup

## 5. 偽の環境に2週間居座った攻撃者の行動記録

t4n4bot4さんの記事。自宅ラボのハニーポット基盤で、SSHの受け口を、攻撃者をログインさせてコマンドを記録するCowrieが受けている。中身は本物のサーバではなく偽の環境だ。あるIPは、その偽の環境を本物の端末だと信じて2週間居座り、偵察し、鍵を植え、cronを仕込み、最後には鍵やパスワードを回収していった。前回は、ハニーポットを見破って去った攻撃者の話だったという。侵入後の行動が時系列で追えるので、守る側が、どの段階で何を見られるかを考える材料になる。

出典: https://zenn.dev/t4n4bot4/articles/c07a7d85356761

## 注目のリリース: AWS Continuum for code vulnerabilities

AWS公式ブログより。AWS Continuum for code vulnerabilitiesが一般提供になった。AIでコードの脆弱性を自動で見つけ、検証し、優先順位をつけて、レビューできる状態の修正をプルリクエストとして届けるサービスだ。これまで調査に数時間、チーム間の調整に数日かかっていた作業を置き換える、とされている。検出が多すぎて本当に危険なものが埋もれる、という悩みがある組織は、まず試す価値がある。

出典: https://aws.amazon.com/blogs/aws/aws-continuum-for-code-vulnerabilities-is-now-generally-available/
